# 闲鱼游戏本 · 方案二：登录 + 只搜搜索页 + 手动 loop + 低频

方案二同样从 v3.0.0 改造，但方向和方案一相反：**恢复 v2 的扫码登录链路，整体移除卖家主页细筛，把节奏交回给人**。

它的职责只有一条：把粗筛通过的闲鱼商品链接整理成待审核报表。商家识别在搜索页完成，跨商品判断（主页挂一串电脑的、大疆卖家）转人工。聊卖家、砍价、下单仍然人工完成。

## 一分钟看懂

```
login.bat 扫码登录（只需一次，登录态落在 data/browser_profile）
  → loop.bat 控制台：start
  → ① 登录态搜索「游戏本」2 页
       进页面点「新发布 → 最新」；超过 24 小时的在粗筛前滤掉
       整页都是见过的老货就提前停
       关键词之间随机停 8–15 秒
  → ② 粗筛（只用搜索页数据，完整保留 v2 的搜索页商家判断）
       商家模块 1：卖家昵称 / 标题 / 商品介绍命中商家词
       可用性：无法开机、开不了机、点不亮
       品牌：苹果、华为
       非整机：求购、租赁、拆机、代拍（否定句豁免）
       继承硬规则：N95、空机、缺内存/硬盘、内存 <8G、硬盘 <120G
  → ③ 直接出待审核报表（不打开卖家主页）
       跨商品商家识别转人工：审核时点开链接，看卖家在售里
       是不是挂着一串电脑/无人机——是就别点联系
       搜索接口自带评价数/好评率/严选身份，直接标注在商品卡片上
  → ④ 停下来等你输入 next（纯手动；距上一轮不足 5 分钟要再确认一次）
  → ⑤ 下一轮，直到 stop / 预算用尽 / 风控 / 登录失效
```

1. Python 3.10+，安装依赖：

```bash
pip install -r requirements.txt
```

2. 装好 Google Chrome（默认用本机 Chrome；`browser.channel: null` 则改用 Playwright Chromium）。

## 开始使用

```bash
# 0. 离线看效果（内置演示数据，不联网、不需要登录）
python -m xianyu scan --demo

# 0.1 回放真实抓包（登录态真实搜索的 30 条原始响应，不联网；临时库，每次干净）
python -m xianyu scan --demo-file tests/fixtures/real_search_20261022.json

# 0.2 回放 v3.8.2 真实轮次抓包（点「新发布 → 最新」后，29/29 新→旧）
python -m xianyu scan --demo-file tests/fixtures/real_search_newest_20261023.json
# 0.3 或整目录回放（tests/fixtures/raw_20261023/ 是 v3.8.2 轮次全部 9 份原始抓包）
python -m xianyu scan --demo-file tests/fixtures/raw_20261023

# 1. 扫码登录（只需一次；登录态过期后重跑）
login.bat

# 2. 控制台循环（推荐日常用法）
loop.bat
#   start 开始循环
#   next  跑下一轮（默认每轮手动确认）
#   stop  立即停止（本轮不出报表）
#   report 打开最新报表
#   exit  退出

# 3. 或者单轮抓一次
scan.bat
# 3.1 改版排查：把搜索接口原文落到 data/captures/
python -m xianyu scan --dump

# 4. 环境自检
python -m xianyu doctor

# 5. D3 积压重筛：按现行规则重过全部待审核（默认 dry-run，--write 才落库）
python -m xianyu rescreen
python -m xianyu rescreen --write
```

计划任务场景用 `run_scan_scheduled.bat`（隐藏窗口、追加日志），但**不建议把频率配高**——方案二的哲学就是低频 + 人在环。

### 推送（可选）

`config.yaml` 里配 `notify.wecom_webhook` 或 `notify.bark_url`，每轮结束后自动推送；`--no-notify` 可临时关闭。

## 粗筛规则（只用搜索页）

与 v3、与 v2 登录版一致，且比 v2 更宽（商家词同时匹配**标题、商品介绍、卖家昵称**）：

- **发布时间窗**：`scan.max_age_hours`（默认 24）在粗筛**之前**过滤，超窗商品进「不符合」，原因「超过发布时间限制」；0 = 不筛；发布时间未知时不过滤。超窗只影响展示：旧待审核只会沉底，不会被自动忽略
- **商家模块 1**：昵称/标题/介绍命中 `signals.merchant` 或 `filters.seller_exclude`
  - `filters.seller_exclude` **只匹配卖家昵称**（v3.7.0 起含「小店、精选、小卖部、购物、优品、笔记本」；v3.8.4 起再加「经销部、电脑、严选、电子、包换、二手、科技、小铺」，共 22 个；标题里正常出现这些词不会误杀）
- **显卡门槛**：识别不到英伟达显卡（1050 及以上）、A 卡/核显、工作站专业卡 → 不符合
- **可用性**：`signals.broken` 里的开机故障词；`signals.boot_reject`（无法开机/开不了机/不开机/点不亮）；`signals.problem_reject`（v3.8.4 新增：问题机、进不去系统、win转圈卡死、处理配件——标题/介绍命中即排除，否定句豁免）
- **品牌**：苹果、华为整机排除
- **非整机**：求购、租赁、拆机、代拍（否定句豁免）
- **继承硬规则**：N95、空机、缺内存/硬盘、内存 <8G、硬盘 <120G

**卖家画像（v3.8.0，只标注不排除）**：搜索接口零额外请求带回评价数、好评率、平台身份（如「闲鱼严选卖家」），解析后落库并在审核页 / 报表 / CSV 展示；评价数达到 `scan.seller_review_hint`（默认 100，0 = 关）时标注「疑似职业卖家」。它**不参与任何排除**——样本量还不够拍硬阈值，先跑几轮看误伤。

## 转人工的部分（原细筛）

以下判断在方案二里**没有自动规则**，靠你审核时多看一眼：

| 原细筛规则 | 人工替代 |
| --- | --- |
| 主页其他商品含「大疆/DJI」→ 排除 | 点进商品页看卖家在售，出现无人机/穿越机就跳过 |
| 主页笔记本 + 配件 ≥5 条 → 商家 | 同样点进卖家在售，挂一串电脑/配件的就是职业卖家 |

代价是明确的：标题干净但主页露馅的职业卖家会进到待审核里，由你筛掉。换来的是每轮基础约 3 个搜索请求（1 个关键词「游戏本」× 初始页 + 排序 + 第 2 页，老货提前停会更少）、不碰卖家主页。

## 待审核、报表与审核页

- 每轮结束立即生成 `reports/` 下的 HTML / CSV / Markdown，`latest.html` 始终指向最新一份
- 报表分两块：**待审核**（粗筛通过）和**不符合**（被粗筛/价格规则/发布时间窗排除，附原因）；不符合明细按扫描编号落库，`report.bat` 重新生成时仍然保留
- **不符合跨轮保留（v3.8.4）**：人工忽略和「积压重筛」移出的记录写在它们**当时那一轮**，不跟着最新一轮走——报表和审核页会额外把它们补进「不符合」，避免跑了新扫描后商品掉进无人区（三个板块都没有）
- **报表「忽略」键（v3.8.4）**：待审核每行有红色「忽略」按钮，点击后经本地审核页服务把商品移入不符合板块（与审核页「忽略」同机制：`status='ignored'` + 人工审核 note，只进不符合、不进自动忽略）；行会置灰、表头计数即时更新。**静态文件本身不写库**：重新生成报表（`report.bat`）后商品正式出现在不符合板块。点击时若提示「审核页服务未启动」，先运行 `review.bat`
- **顶栏「价格区间」（v3.8.4）**：顶栏有一组「价格区间」输入框（最低 / 最高）+ 「清除」按钮，输完即时生效。待审核与不符合**两个板块都按价格过滤**，方便只看某个价位段（也便于核对某价位有没有被误杀）。只填一边 = 单边区间；最低 > 最高会自动交换；发布时间未知/价格缺失的商品不过滤。**纯前端显示筛选**：不写库、不影响抓取范围、不发请求；设置记在本机 localStorage，下次打开同一份报表仍在
- 待审核卡片带卖家画像标注：评价数 / 好评率 / 平台身份，高评价数（`scan.seller_review_hint`）加「疑似职业卖家」徽标——**只标注，不排除**
- 审核页待审核排序（v3.8.0）：时间窗内靠前（按发布时间新→旧）→ 过期沉底 → 发布时间未知排最后；只影响审核页，静态报表仍按首次出现排序
- 数据库跨轮保留：没审核完的商品下一轮报表继续列出；历史条目不单独标「上轮」，在审核页「全部」里看
- 本地审核页：`python -m xianyu review`（或 `review.bat`），只监听 `127.0.0.1`，浏览器里点按钮标记状态

### 审核页状态流（v3.7.0）

| 操作 | 落库 | 之后出现在 |
| --- | --- | --- |
| 待审核卡片点「忽略」 | `listings.status = ignored`、`note = 人工审核`，同时把快照写进**最新一轮**的 `scan_rejects`（`reason = 人工审核`） | 新增的「不符合」标签，人工记录排最前 |
| 人工不符合卡片点「恢复待审核」 | `status = pending`、`note` 清空，并删除这条人工不符合记录 | 回到「待审核」 |
| 规则/粗筛忽略的商品 | `note` 是规则原因 | 「自动忽略」标签（`note` 以 `人工审核` 开头的不在这里重复展示） |

两条边界要说清楚：

- **粗筛不符合没有「恢复」键**：粗筛阶段排除的商品从不写入 `listings`，恢复需要先确定「补建 listing」的数据来源，属于尚未设计的功能。
- **静态报表不会自动更新**：点按钮（含 v3.8.4 的报表「忽略」键）只改数据库，`reports/latest.html` 是文件——忽略键点完行会置灰、计数即时更新，但商品正式进不符合板块要重新生成报表（运行 `report.bat`，离线、只读本地库；它读最新一轮的 `scan_rejects`，再把跨轮的人工/重筛记录补上）或等下一轮扫描。价格区间属于纯前端筛选，不受此限制——改完立即生效。

### D3 积压重筛（v3.8.3）

规则变更（v3.6 显卡门槛、v3.7 卖家词、v3.8.0 时间窗）会留下一批按旧规则入库的待审核。`python -m xianyu rescreen` 用**同一套现行规则**重过全部待审核：

- 默认 **dry-run**，只打印「保留 N / 移出 M」和原因分布；`--write` 才落库
- 落库建一轮**专用「人工重筛」轮次**（不发任何请求，`sort_status` 有标记，不会和真实轮混淆）：移出商品写进该轮 `scan_rejects`（原因 = 规则原因），`listings` 置 `ignored`、`note='重筛排除：<原因>'`——和「人工审核」一样只进不符合板块，不进自动忽略
- 规则优先级与引擎一致：**先查 24 小时时间窗，再查粗筛**；超窗商品记「超过发布时间限制」（同时命中商家词等次因时被时间窗掩映，与扫描路径行为相同）
- 通过的商品一律不动；没有可移商品时不建轮次（重复执行幂等）；写入走 `scan.lock`，与真实扫描互斥
- 移出的商品和粗筛不符合一样**没有恢复键**（数据都在 `scan_rejects` 快照里，必要时可人工补建）；v3.8.3 已对真实积压执行过一次（轮次 #7：158 → 保留 107 / 移出 51），写库前备份 `data/xianyu.db.bak-before-d3-20261023`

## 风控与运行策略

| 机制 | 行为 |
| --- | --- |
| 登录态检测 | 每轮搜索前检查 `unb/sn/uc1/lgc`；`unb` 缺失立即停并提示重新扫码，其余缺失只告警 |
| 轮次节奏 | **纯手动**：每轮结束输入 `next` 才继续；相邻两轮默认至少 5 分钟，提前 `next` 需再输入一次确认（`loop.min_round_gap_seconds`） |
| 关键词间隔 | 每个关键词之间随机停 8–15 秒（`browser.min/max_delay`） |
| 每日预算 | `scan.daily_request_budget`（默认 200）按**实际发出的搜索接口请求**计数，落盘到 `data/request_budget.json`，`scan`/`loop` 共用、跨进程累计、跨天重置 |
| 新发布筛选 | 只在筛选面板内用 DOM click 点「新发布 → 最新」（绕开拦截 Playwright 点击的 1200×1200 图片遮罩）；「最新」与「1天内」是同组互斥子项，点「最新」拿真时间序，24 小时窗由 `scan.max_age_hours` 客户端筛；点击后校验仍在搜索页，点进商品页/开新标签立即停本轮；控件找不到或点不到就按默认排序并告警；每个关键词多 1 次搜索请求 |
| 翻页 | 每页只点一种翻页方式；点完没等到新请求或动作抛异常就结束本轮，不换方式补点 |
| 排序状态 | 每个关键词的点击结果 + `publishTime` 反查写入 `scans.sort_status`、控制台和报表；没点成功或返回不是新→旧都会告警 |
| 搜索风控 | 人机验证/处罚：连续 `failure_threshold` 轮 → 24 小时起，翻倍升级 |
| 频率限制 | 「请求频率或额度已超限」：`rate_limit_threshold`（默认 1）次即冷却 30 分钟，连续命中翻倍，上限 12 小时 |
| 软失败 | 超时/结构异常/0 结果 → 软冷却 1–24 小时 |
| Baxia 弹窗 | 有头模式暂停等你处理（默认 120 秒），超时才判风控；等待不计入抓取超时 |
| 登录失效 | 不计数、不进熔断，直接停循环（这是要人扫码，不是冷却） |
| 风控即停 | 循环里检测到风控立即停止，不自动重试 |

**要知道的代价**：登录不会免疫风控（v2 登录版自己就带三套熔断计数器），它只是把风控后果从"IP 临时冷却"升级成"账号要验证"——闲鱼号绑着阿里系信用，账号级代价更大。所以方案二把频率压得比方案一还低，并且把手放在环里。

## 反检测加固（借鉴 Scrapling）

浏览器启动后注入 5 条 bypass 脚本（`browser.stealth: true`，可关），并清理
`--enable-automation` 等 5 个 Playwright 默认参数：

| 脚本 | 作用 |
| --- | --- |
| `webdriver_fully.js` | 把 `navigator.webdriver` 伪装成原生 getter |
| `window_chrome.js` | 补全 `window.chrome`（app/csi/loadTimes） |
| `navigator_plugins.js` | 补 5 个 PDF 插件 |
| `notification_permission.js` | `Notification.permission` 固定 default |
| `playwright_fingerprint.js` | 删除 Playwright 运行时痕迹 |

借鉴自 Scrapling v0.3.10（BSD-3-Clause，`github.com/jasonking0112/Scrapling`），
代码在 `xianyu/stealth_bypasses/bypasses/`，加载与注入逻辑在 `xianyu/stealth.py`。
**方案二尤其值得保留**：登录态下被识别成自动化的后果是账号级。

**实测结论（2026-10-22，Chrome 151 + 当前 Playwright，headless 对照实验）**：
这套脚本在当前环境下基本空转——`navigator.webdriver` 由 Blink 内部控制，JS 盖不住，
真正让它变 false 的是启动参数 `--disable-blink-features=AutomationControlled`
（crawler 一直在传）；新版 headless Chrome 自带 5 个 PDF 插件、`window.chrome` 本就存在、
Playwright 的 `__pwInitScripts` 痕迹在当前版本已不存在。上游的 `screen_props.js`
实测有害（会把真实窗口值 1280 覆盖成采集机的 1313），已移除。
保留注入的成本是 5 个小文件，价值是版本兜底；**真正保账号的仍是低频 + 手动确认 +
最小请求量**，脚本只是锦上添花。

## 配置怎么改

所有可调参数都在 `config.yaml`，改完重启生效。方案二相关的关键项：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `browser.require_login` | `true` | 搜索前必须已登录（`login.bat`） |
| `browser.headless` | `false` | 有头运行：看得见页面，风控时能立刻停 |
| `browser.min/max_delay` | `8`/`15` | 关键词之间的随机间隔（秒） |
| `browser.baxia_wait_seconds` | `120` | 遇到 Baxia 滑块时等人处理的秒数 |
| `scan.newest_first` | `true` | 进页面点「新发布 → 最新」；`false` = 闲鱼默认排序 |
| `scan.max_age_hours` | `24` | 客户端发布时间窗（小时）：粗筛前滤掉超窗商品；0 = 不筛；时间未知不过滤 |
| `scan.seller_review_hint` | `100` | 卖家画像标注阈值：评价数达到就在审核页/报表标「疑似职业卖家」；**只标注不排除**；0 = 关 |
| `scan.stop_on_known` | `true` | 整页都是见过的老货且确实是新→旧时，提前结束翻页 |
| `scan.rate_limit_threshold` | `1` | 命中限流几次后开始短冷却 |
| `scan.rate_limit_cooldown_minutes` | `30` | 限流冷却起点，连续命中翻倍 |
| `scan.rate_limit_max_minutes` | `720` | 限流冷却上限（12 小时） |
| `scan.daily_request_budget` | `200` | 每日搜索请求上限，落盘累计，0 = 不限 |
| `loop.reuse_browser` | `true` | 跨轮复用浏览器，不每轮重启 |
| `loop.min_round_gap_seconds` | `300` | 相邻两轮最小间隔；提前 `next` 需再确认一次，0 = 不限制 |
| `watches` | 1 个关键词（游戏本） | 想广就照格式加词；每加一词每轮约多 3 个请求 |

`fine` 配置段保留只为兼容旧文件，**开着也不会打开卖家主页**（引擎已移除该阶段）。

## 已知边界

- 登录态过期不会自动续，扫码重登即可（`login.bat`）
- 每轮 1 个关键词 × 2 页 ≈ 60 条覆盖（2026-10-23 主人要求收缩请求量；历史数据里「游戏本」通过率约 39%，另两词合计再多约 44 条通过，需要时可在 `watches` 加回）
- 提前停依赖「新发布 → 最新」真的点成功；返回顺序不是新→旧时会退回正常翻页（有日志告警），不会漏新货但会多翻页
- 实跑已确认：筛选面板和「新发布 / 最新」文本都存在，但页面有一层 1200×1200 图片遮罩会拦截 Playwright 的正常点击；筛选改用面板内 DOM click，只命中这两个文本节点，不依赖坐标，也不会点到商品卡片。若后续改版导致文本不在面板内，会降级为默认排序并在报表里标出，不会误点商品
- 「最新」是排序子项，理论上给真时间序，但服务端行为只能信数据：每页用 `publishTime` 反查，顺序没落地（返回不是新→旧）时不提前停、按页翻完，并在 `scans.sort_status` 和报表里显式告警
- **追新仍有索引延迟上限**：v3.8.0 已把点子项从「1天内」换回「最新」（真实 A/B：#3 轮「顺序已确认新→旧」）；2026-10-23 06:41 最小实跑再次确认顺序新→旧，且页 1 的 30 条发布跨度只有 9.6 分钟、全部落在 6.03–6.19 小时前——当前索引最新样本约 6 小时（#3 轮为 9–14 小时）。24 小时窗由 `scan.max_age_hours` 客户端筛；追到「几十分钟前」取决于发布密度 + 索引批次，不是脚本能压掉的
- 卖家画像只标注不排除：「疑似职业卖家」徽标依赖 `scan.seller_review_hint`（默认 100），阈值是展示口径不是判定口径；真实样本 n=30 太少，升级成硬门槛前先跑几轮看误伤
- 点排序本身会多发 1 次搜索请求（每个关键词第 1 页一次）；这是拿准确排序换来的固定成本
- 轮次间隔是软下限，不是硬限制：确认第二次 `next` 仍可提前开跑；每日预算的日期按本机时区计算
- N 卡只从搜索页的标题/描述文本识别，且只认 1050 及以上型号：没写显卡型号、或只写 GTX 9 系（如 950M）的整机会被排除，可在「不符合」里逐条复查
- 跨商品商家识别转人工后，待审核量会变多——这是设计取舍，不是 bug
- `loop` 需要交互式控制台；计划任务用 `run_scan_scheduled.bat`（单轮）

## 常见问题

**Q：和方案一（`../option1-cdp`）怎么选？** 方案一保留自动细筛、匿名、风控后果轻，但请求画像再像真人也有概率被识别；方案二请求极少、人在环里最稳，但代价是登录账号暴露在风控后果里 + 细筛转人工。两个都做出来了，建议先跑方案一几天，风控压不住再切方案二。

**Q：loop 会自动跑吗？** 不会。每轮结束必须输入 `next`，没有自动续跑；距上一轮不足 5 分钟时，第一次 `next` 只提示，再输入一次才放行。单轮异常直接停，需要你处理后重新 `start`。

**Q：为什么报表里没有几十分钟前的新货？** v3.8.0 起已经换成确定性追新：点「新发布 → 最新」拿真时间序（不再点互斥的「1天内」丢排序），24 小时窗由客户端 `scan.max_age_hours` 筛；2026-10-23 06:41 实跑确认排序生效（顺序已确认新→旧）。剩下的延迟来自闲鱼搜索索引本身——实跑时「最新」页 1 的 30 条全部在 6.03–6.19 小时前（跨度 9.6 分钟），说明索引按批次更新；这是平台侧行为，脚本压不掉。想再缩短只能加页数（更多真实请求），需要先批准。

**Q：登录态存在哪？** 真实 cookie 在 `data/browser_profile`（Playwright 持久 profile），`data/login_state.json` 只是登录标记（用户 ID + 时间），供自检和过期判断。
